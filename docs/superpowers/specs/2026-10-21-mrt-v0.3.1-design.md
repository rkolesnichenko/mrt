# mrt v0.3.1: DecompressWith hardening

Status: implemented, 2026-10-21. The cap is 2 MiB (largest real block 981,320 bytes, `.data/v031-blocks.log`). Amends the v0.3 design
(`docs/superpowers/specs/2026-10-20-mrt-v0.3-design.md`, "v0.3" below) where
it says so. The user asked for v0.3.1 and opted out of questions; every
decision below not quoted from the user or from v0.3 is the author's call and
is marked so.

## 1. Intent

v0.3.0 shipped `DecompressWith`. Its release left items open (PR #6, "Open,
for the next release", and an automated security review of the push). v0.3.1
closes them without changing the API, so routecheck and every other consumer
is untouched.

The main one is memory on hostile input. v0.3's anti-goal 4 is "unbounded
memory or CPU on hostile input". v0.3.0 is bounded, but its bound grows with
the worker count: `2 × Workers × (8 MiB + ~2 × 46.6 MB)` (v0.3 §6.2). The
CLIs pass `Workers: GOMAXPROCS`, so on a 14-core machine that formula gives
about 2.8 GB for one crafted file (arithmetic, not measured). A valid bzip2
file needs no crafting to come close: `bzip2 -9` (1.0.8) puts 45,899,235
bytes of zeros in each block, and 465 MB of zeros compress to 369 bytes in 11
blocks (`.data/zeros-blocks-probe.log`).

## 2. Goals

1. **A memory bound of `fixed + Workers × per-worker`, with a small
   per-worker term.** v0.3.0's per-worker term is about 2 × (8 MiB + 93 MB)
   for a hostile block; v0.3.1's is bounded by a cap on speculative output
   (§5.3). Nothing the reader holds grows with the input.
2. **A cancel takes effect after the block being decoded**, as the
   `DecompressWith` doc already says. Today a worker may first take queued
   jobs (v0.3 final review M1/N1).
3. **No speculative work past its use.** A speculative decode stops once its
   output passes the cap or it has read past its segment (v0.3 final review
   M5: today it keeps decoding zeros).
4. **mrtcut on gzip: measured**, and changed only if the measurement shows it
   slower than `Decompress` and the user picks the fix (§5.5).
5. **The two doc fixes**: the `DecompressWith` doc says it reads the first
   bytes of `r` before returning; the v0.3 plan points to the post-fix gate
   log.
6. **Speed unchanged on real data** at W4 and W14 (§6).

## 3. Non-goals

- **Any exported change.** `api/` stays byte-identical; no new option, no
  knob for the limits (author's call: a knob is API, and these are internal
  safety limits, not tuning parameters).
- **Changing `Decompress`.** It stays exactly as it is.
- **Streaming the chain's serial decode.** The chain still decodes one whole
  block when it decodes serially, as v0.3 does: about 93 MB transient for a
  hostile block, once, whatever `Workers` is (v0.3 Ruling 12).
- **Capping the CLIs' worker count.** With goal 1 the per-worker term is
  about 17-26 MB (§5.3), so the CLIs keep `GOMAXPROCS` (author's call).
- **The gzip copy-only slowdown in general** (0.83×,
  `.data/decompress-v03-gate-gzip.log`). A `WriteTo` on the gzip readahead
  might remove it; `io.Copy` would then take a different path, so it waits
  for the user.
- **The other deferred minors in the v0.3 ledger** not named in §5 (stale
  `fileCRC` comments, error-after-first-error docs, false magic inside a block
  making it serial, the 50% bound in `TestMrtdumpWriteErrorStops`,
  `TestRealData` fataling without bgpdump, file length). They stay parked.

## 4. Anti-goals (a failure even if it works)

- **A different byte or a different error** from `Decompress`, on any input.
  v0.3's anti-goal 3 stands; the speculation may give up more often, never
  differ.
- **Slower on real files.** A cap or budget that real blocks hit, so they fall
  back to serial, defeats v0.3. Real level-9 blocks decode to about 0.9 MB on
  average (rv2: 1,260,879,356 bytes in 1,403 blocks; rv6: 471,448,090 in 512;
  `.data/decompress-v03-gate-bzip2-fix.log`).
- **A consumer break.** No exported signature or behaviour a caller can
  observe changes, other than memory and how soon a cancel takes effect.

## 5. Design

### 5.1 Speculative output cap

- Speculative (worker) decodes get an output cap; the chain's own decodes get
  none (they must give exactly what `compress/bzip2` gives).
- A worker's decode that passes the cap stops filling chunks and returns **no
  data** and a result the chain never takes (as `whole == false` is today).
  It does not make the exact-size copy, so it never holds more than the cap
  plus one 1 MiB chunk. The chain decodes that block itself when it reaches
  it.
- **The cap's value** (author's call): the smallest power of two that is at
  least twice the largest decoded block in the six real bzip2 files
  (`.data/realdata/MANIFEST`: rv2-rib, rv6-rib, four rv2-updates), and at
  least 2 MiB. Provisional, before that measurement: 4 MiB. The cap changes
  only the per-worker term of §5.3.
- How the cap reaches `internal/bzip2` (a Decoder field, a second Block entry
  point, an option) is the builder's choice; `Block`'s existing behaviour,
  used by the chain and `NewReader`, does not change.

### 5.2 Stop past the segment

- A speculative decode whose bit reader has failed (it read past its segment)
  returns no data, checked once the block's Huffman and BWT stage
  (`readBlock`) is done and before any output is produced (author's call).
  That leaves the copied standard code unchanged (block.go's promise); the
  wasted CPU is at most one block's `readBlock` on zero bits, bounded by the
  block size. The chain's decodes are unaffected: they keep compress/bzip2's
  behaviour of decoding a cut block from zero bits.

### 5.3 The bound

What the parallel reader holds, term by term (author's call, after the
builder check):

| Term | Bound | Limited by |
|---|---|---|
| Segment copies of outstanding jobs | 32 MiB in all | **new:** a hard budget; a segment's size is known at dispatch, so a job that would pass it waits (any one segment is at most 8 MiB, so a job always fits once the others are taken) |
| Results finished but not yet taken by the chain | 2 × Workers × cap | v0.3's 2 × Workers outstanding, and the cap (§5.1) |
| Each worker's decode | 3.6 MB block table + up to cap + 1 MiB of chunks + the exact-size copy (at most cap) | the cap |
| The compressed window | up to 2 × (8 MiB + 2 × Workers MiB): v0.3's lead limit, and the window compacts only when half is dead | v0.3, unchanged |
| The chain's serial decode | one block, ~93 MB transient for a hostile one | v0.3 Ruling 12, unchanged |

- So: `fixed ≈ 32 MiB + 16 MiB + 93 MB ≈ 143 MB`, plus per worker
  `3.6 MB + 4 × cap + 5 MiB`. At cap 4 MiB that is about 25.6 MB per worker,
  about 500 MB at W14. At cap 2 MiB, about 17 MB and 385 MB. v0.3.0's
  results alone are up to 2 × Workers × 93 MB, about 2.6 GB at W14. All of
  these are arithmetic from the formulas until §6 measures.
- Results are not given a byte budget of their own: their size is unknown
  until a worker sends them, and a worker-side budget would make which blocks
  are speculated depend on timing. The count limit times the cap bounds them
  instead (author's call).
- Real data: segments are about 55 KB (rv2: 76,399,889 compressed bytes in
  1,403 blocks), so the 32 MiB budget should never bind; §6 checks speed.

### 5.4 Cancel and stop drain the queue

- `stop()` (on cancel, error or end) makes sure no worker starts a queued job
  after it is called: queued jobs are drained or skipped, and a worker checks
  for stop before taking each job. Each worker finishes at most the block it
  is decoding.
- The `DecompressWith` doc's cancel sentence then holds as written. A test
  pins it: with jobs queued behind slow workers, a cancel ends with no worker
  having started a job after the cancel (a test hook may count job starts).

### 5.5 mrtcut on gzip

- mrtcut's real inputs are RouteViews `.bz2` (v0.3 Ruling 15), so this is a
  check, not a known problem. Measure `mrtcut` on the rrc00 bview `.gz` (read
  only, never committed: R18) with `Decompress` and with `DecompressWith`,
  each run alone under the heavy-run rules, and log it.
- If `DecompressWith` is not slower, nothing changes and the CHANGELOG gives
  the figure. If it is slower, nothing changes in this release either: the
  result goes to the user with the two fixes (a format check in mrtcut, which
  duplicates the library's, or `WriteTo` on the readahead, §3), and they pick.

### 5.6 Docs

- `DecompressWith` doc: before it returns it reads from `r`: the first bytes
  to tell the format and, for gzip, the whole gzip header (`gzip.NewReader`),
  so `r` must be ready to be read when it is called. The memory sentence
  states §5.3's worst case.
- The v0.3 plan gets one line pointing to
  `.data/decompress-v03-gate-bzip2-fix.log` as the gate result that counts.
- CHANGELOG `[Unreleased]`: the new bound with its log, the cancel fix, the
  mrtcut result, and what was not measured.

## 6. Tests and gates

- **Equivalence (unchanged rules):** every existing fixture, the 19 real
  files (`TestRealData/decompress-with/<file>`), `FuzzBzip2`,
  `FuzzDecompress`: byte- and error-identical to `Decompress`.
- **New committed fixtures** (author's call on the split):
  - For unit tests: zeros through `bzip2 -1`, 12 blocks of 5,099,235 bytes
    (the last 3,908,415), 388 bytes in all (`.data/zeros1-blocks-probe.log`:
    `head -c 60000000 /dev/zero | bzip2 -1`). Each block is over a 4 MiB cap.
    If §5.1's measurement sets the cap above 5.1 MB, the unit fixture uses
    the next level whose zero blocks are over the cap.
  - For the memory gate only, never decoded by `go test`: zeros through
    `bzip2 -9`, 11 blocks of 45,899,235 bytes, 369 bytes in all
    (`.data/zeros-blocks-probe.log`), about 465 MB of output.
  - Decompressed sizes are checked, never committed.
- **Unit tests are deterministic** (no heap sampling: it depends on GC timing,
  `-race` and CI load). Through test hooks:
  - the segment copies never exceed 32 MiB in all, and outstanding never
    exceeds 2 × Workers, on the unit zero fixture, v0.3's crafted inputs and
    the fixtures, at Workers 1, 3, 4 and 16 (the plan may drop worker counts
    if `go test ./...` would leave "near a minute");
  - on the unit zero fixture at W4, every block is capped and taken
    serially, and the output is identical;
  - stop past the segment (§5.2): a candidate whose segment is cut short
    returns no data;
  - cancel (§5.4).
- **Gates, each logged under `.data/`, run alone under the heavy-run rules,
  v0.3.0 and v0.3.1 measured in the same run:**
  - Speed: rv2 and rv6 decompress-only at W4 and W14. v0.3.1 within 5% of
    v0.3.0 at each worker count.
  - Largest decoded block across the six real bzip2 files (for §5.1).
  - Memory: peak heap (sampled) at W4 and W14 on the `-9` zero fixture and
    on v0.3's crafted inputs (end-magic flood, sparse garbage). Pass: v0.3.1
    under §5.3's worst case on every input. On the `-9` zero fixture, v0.3.0
    is expected above it; the other inputs only report v0.3.0's figure.
  - mrtcut (§5.5).
- `check.sh` with `FUZZTIME=15s` ends `check: ok`; `api/` unchanged;
  routecheck's build errors against the branch equal those against v0.2.1
  (as in v0.3, its Ruling 16).

## 8. Builder check

A builder read the first draft. Their questions and the answers now above:
the bound left out finished-but-untaken results and the exact-size copy
(§5.3's table now counts them); a hard byte budget on results would cut W14's
parallelism or make speculation timing-dependent (results are bounded by
count × cap instead, and only segment copies have a byte budget); the `-9`
zero fixture would cost over 2 GB of output in the race suite (unit tests use
`-1`); stopping mid-Huffman would edit the copied code (§5.2 checks after
`readBlock`); only six real files are bzip2 (§5.1); the gzip header is read
too (§5.6).
