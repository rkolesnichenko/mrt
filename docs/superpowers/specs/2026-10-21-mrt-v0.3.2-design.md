# mrt v0.3.2: the items left open by v0.3.1

Status: draft, 2026-10-21. Amends the v0.3.1 design
(`docs/superpowers/specs/2026-10-21-mrt-v0.3.1-design.md`, "v0.3.1" below)
where it says so. The user asked for v0.3.2 and opted out of questions. Every
decision below that is not quoted from the user or from v0.3.1 is the
author's call and is marked so.

## 1. Intent

v0.3.1 shipped with four items open (CHANGELOG `[0.3.1]`, PR #7 "Open, for
the next release"). v0.3.2 closes them without changing the API, so
routecheck and every other consumer is untouched:

1. **mrtcut is slower on gzip.** `mrtcut -count` on the rrc00 bview `.gz`
   took 7.253 s with v0.2.1 and 7.778 s with v0.3.1, a mean of 4 alternating
   runs (+7.2%). v0.2.1 ran at 7.23-7.28 s. v0.3.1 alternated between 8.30 s
   and 7.26 s (`.data/v031-mrtcut-gz.log`). The cause is unknown.
2. **`Decompress` keeps a drained block live** while it decodes the next one
   (`internal/bzip2/block.go`, `streamReader.Read`). v0.3.1 fixed the same
   pattern in the parallel reader (9c559b1) but kept `Decompress` unchanged.
3. **Two terms of the bzip2 bound are only arithmetic.** These are the
   segment copies (32 MiB) and the results finished but not yet taken
   (2 × Workers × 2 MiB). No measured input loads them (CHANGELOG `[0.3.1]`,
   Not measured).
4. **Test and tool housekeeping**, deferred by the v0.3.1 reviews (§5.4).

## 2. Goals

1. **Know why mrtcut is slower on gzip, and remove the slowdown if it is
   real** (§5.1).
2. **`Decompress` drops a drained block** before it decodes the next one.
   Its bytes and errors are unchanged (§5.2).
3. **Every term of the bound is measured on an input that loads it**, or the
   doc says which term no input can reach and why (§5.3).
4. **The housekeeping list is done** (§5.4).

## 3. Non-goals

- **Any exported change.** `api/` stays byte-identical, as in v0.3.1.
- **`WriteTo` on the gzip readahead.** It would only help callers that use
  `io.Copy`. mrtcut, mrtdump and routecheck read through `Records`, which
  wraps its input in a `bufio.Reader` (reader.go:68-70) and reads it in 4 KiB
  calls, so `WriteTo` cannot speed any of them up. v0.3.1's CHANGELOG names
  it as a possible mrtcut fix; that note is wrong and §5.5 corrects it. The
  copy-only gzip slowdown it might fix (0.83×,
  `.data/decompress-v03-gate-gzip.log`) stays parked (author's call: no
  measured consumer copies).
- **Changing `Records`' buffer size.** It would change how much every caller
  reads ahead of a record error.
- **Capping the CLIs' worker count.** The bound of v0.3.1 stands.

## 4. Anti-goals (a failure even if it works)

- **A different byte or a different error** from `Decompress` or
  `DecompressWith` on any input (v0.3 anti-goal 3, v0.3.1 §4).
- **Slower on real files.** That covers the v0.3.1 speed gate (rv2, rv6 at W4
  and W14) and the v0.3 gzip gate (`Decompress`+Routes vs
  `DecompressWith`+Routes on the rrc00 bview, 1.47×).
- **A fix chosen before the cause is known.** §5.1 measures first.

## 5. Design

### 5.1 mrtcut on gzip: diagnose, then decide

**Diagnose** (each run alone, under the heavy-run rules, logged under
`.data/`):

- **The series.** `mrtcut -count` on the rrc00 bview `.gz`, 10 alternating
  pairs: v0.2.1 (`Decompress`) and the branch (`DecompressWith`, Workers =
  GOMAXPROCS). Four runs cannot tell an alternation from noise. Ten pairs
  can show whether the two speeds are real and whether v0.2.1 ever shows
  them too.
- **The split.** The same file through decompression alone (`decompbench`'s
  gzip path, `Decompress` vs `DecompressWith`) and through
  `Records` alone. That separates the readahead's cost from record parsing.
- **A CPU profile of a slow run and of a fast run** of the branch. mrtcut gets
  a `-cpuprofile` flag; it is a test-only tool, so the flag is not API. Add
  `GODEBUG=gctrace=1` on one of each. The slow runs of v0.3.1 also differ in
  memguard's own report lines (their stdout hashes differ:
  `.data/v031-mrtcut-gz.log`), so log memguard's full output too.

**Decide** (author's call; the user opted out of questions). The mean is
taken over the 10 pairs:

- **Under 3% slower:** noise or a negligible cost. No code change. The
  CHANGELOG gives the figure and corrects v0.3.1's note.
- **3% or more, and the profile puts the cost in the readahead** (the
  goroutine handoff, the per-Read `ctx.Err()`, the 32 KiB chunk size): fix
  it inside the readahead. Such a fix must:
  - bring mrtcut within 3% of v0.2.1;
  - not slow the v0.3 gzip gate (`DecompressWith`+Routes) by more than 5%;
  - keep the 256 KiB queue bound.
- **3% or more, and no readahead fix meets that:** mrtcut opens gzip inputs
  with `Decompress`. It checks the gzip magic itself, three bytes through
  the `bufio.Reader` it already needs, and keeps `DecompressWith` for bzip2.
  This duplicates three lines of the library's format check (accepted; it
  is an internal tool).

Whatever the outcome, the CHANGELOG states the cause as found, or says it
was not found.

### 5.2 `Decompress` drops a drained block

- `streamReader.Read` sets `data` to nil once it is empty, as the parallel
  reader does since 9c559b1. Its output and errors do not change.
- This amends v0.3.1 §3 ("`Decompress` stays exactly as it is") for this one
  line (author's call). It changes only how long a block stays reachable.
  routecheck reads through `mrt.Decompress` (its `internal/cli/load.go`), so
  it gains from this once it upgrades.
- A test pins it in `internal/bzip2`, in the package, with no heap sampling,
  as `TestDecompressWithDropsDrainedBlock` does for the parallel reader.

### 5.3 An input that loads the bound

- **A synthetic input, built in memory by `decompbench -crafted`.** It is not
  committed if it is larger than the fixtures allow (`testdata/` stays under
  15 MB). It drives the two unmeasured terms as high as the reader's other
  limits let them go, at W4 and W14:
  - **Results finished but not taken:** blocks that decode to just under the
    2 MiB cap, behind a block the chain decodes serially (one over the cap),
    so workers finish ahead of the chain.
  - **Segment copies:** blocks whose compressed segments are as large as the
    window allows.
- **Reading the terms.** The memory gate reports each term's peak from test
  hooks, next to the heap figure. The terms are `segHeld`, and the bytes of
  results received but not taken, which needs a hook of its own. The
  builder may find that a term cannot reach its bound at some worker count.
  For example, segment copies of outstanding jobs cover distinct ranges
  ahead of the chain, so they may be limited by the window (8 MiB +
  2 × Workers MiB) before the 32 MiB budget. Then the doc says so, and the
  bound's arithmetic may tighten. It must never loosen without a measured
  input that passes it.
- **Pass:** v0.3.2's GOGC=10 peak growth stays under the documented bound on
  this input, as on zeros-9 (v0.3.1 Ruling 9's method, unchanged).

### 5.4 Housekeeping

From the v0.3.1 task and final reviews:

- **Zero fixtures to a subdirectory.** `zeros-1.bz2` and `zeros-9.bz2` move to
  `testdata/bzip2/zeros/`, so the three `[^z]*.bz2` globs go back to
  `*.bz2`. Fix `testdata/README.md` and every path that names them.
- **Test cost.** `TestDecompressWithCappedDamaged` decodes 3 offsets under
  `-race` instead of 5 (about 15 s under `-race`). The redundant re-decode in
  `TestSpeculativeBlockCap` goes.
- **`TestDecompressWithCancelDuringSerialBlock` passes on v0.3.0 too.**
  Rename it to what it pins: a cancel between Reads of capped blocks ends
  with `context.Canceled` and no goroutine left. Its doc says it is a
  regression test; `TestDecompressWithCancelStartsNoJob` pins the v0.3.1 fix.
- **Gaps in Task 1's tests:**
  - The last zeros-1 block at a 4 MiB cap is not compared to `Block`'s
    result.
  - `TestSpeculativeBlockPastInput` passes without `SpeculativeBlock`'s
    past-input check (`br.err != nil`, block.go:137); make it fail without
    it.
  - Nothing tests that extra chunks are dropped after a capped call.
  - One test's failure messages skip block numbers.
- **Docs and tools:**
  - The `internal/bzip2` file comment names `SpeculativeBlock`.
  - `decompbench -blocks` prints no cap when every file failed.
  - `decompbench -mem -crafted` runs with no FILE.

## 6. Tests and gates

- **Equivalence (unchanged rules):** every fixture, the 19 real files
  (`TestRealData/decompress-with/<file>`), `FuzzBzip2` and `FuzzDecompress`.
- **Speed:** the v0.3.1 speed gate (rv2, rv6, W4 and W14). v0.3.2 must be
  within 5% of v0.3.1, both measured in the same run. If §5.1 changes the
  readahead, the v0.3 gzip gate runs too.
- **Memory:** v0.3.1's gate on zeros-9 and on the new input (§5.3), at W4 and
  W14, under GOGC=10, with the default-GC figure reported next to it.
- **mrtcut:** the §5.1 series, before and after any change.
- **Checks:** `check.sh` with `FUZZTIME=15s` ends `check: ok`. `api/` is
  unchanged. routecheck's build errors against the branch equal those
  against v0.2.1.
