# mrt v0.3.2: the items left open by v0.3.1

Status: implemented, 2026-10-21. Amends the v0.3.1 design
(`docs/superpowers/specs/2026-10-21-mrt-v0.3.1-design.md`, "v0.3.1" below)
where it says so. The user asked for v0.3.2 and opted out of questions. Every
decision below that is not quoted from the user or from v0.3.1 is the
author's call and is marked so.

## 1. Intent

v0.3.1 shipped with items open (CHANGELOG `[0.3.1]`, PR #7 "Open, for the
next release"). v0.3.2 closes them without changing the API, so routecheck
and every other consumer is untouched:

1. **mrtcut is slower on gzip.** `mrtcut -count` on the rrc00 bview `.gz`
   took 7.253 s with v0.2.1 and 7.778 s with v0.3.1, a mean of 4 alternating
   runs (+7.2%). v0.2.1 ran at 7.23-7.28 s. v0.3.1 alternated between 8.30 s
   and 7.26 s (`.data/v031-mrtcut-gz.log`). The cause is unknown.
2. **The bzip2 bound is mostly arithmetic.** zeros-9 loads the chain's
   serial decode and the workers' capped decodes. The crafted inputs end at
   their first block. Nothing measured loads these terms:
   - the segment copies;
   - the results finished but not yet taken;
   - the compressed window;
   - the exact-size copy a worker makes for a block under the cap.
3. **Two statements in v0.3.1 are wrong** (found by the v0.3.2 builder
   check):
   - It says `Decompress` keeps a drained bzip2 block live (CHANGELOG
     `[0.3.1]`, Not measured; v0.3.1 §5.3 amendment). It does not.
     `Decompress` decodes bzip2 with the standard library's
     `compress/bzip2` (decompress.go:5, :29), which copies output straight
     from its block table into the caller's buffer. Only `internal/bzip2`'s
     serial `streamReader` has that pattern, and only its own tests use it.
   - It names `WriteTo` on the gzip readahead as a possible mrtcut fix
     (CHANGELOG `[0.3.1]`). mrtcut reads through `Records`, which wraps its
     input in a `bufio.Reader` (reader.go:68-70) and reads it in 4 KiB
     calls. `WriteTo` only helps `io.Copy` callers, so it cannot change
     mrtcut.
4. **Test and tool housekeeping**, deferred by the v0.3.1 reviews (§5.4).

## 2. Goals

1. **Know why mrtcut is slower on gzip, and remove the slowdown if it is
   real** (§5.1).
2. **Every term of the bzip2 bound is measured on an input that loads it**,
   or the doc says which term no input can reach and why (§5.2).
3. **The two wrong statements are corrected** where users read them (§5.5).
4. **The housekeeping list is done** (§5.4).

## 3. Non-goals

- **Any exported change.** `api/` stays byte-identical, as in v0.3.1.
- **Changing `Decompress`.** It already holds no decoded block beyond the
  standard library's own state (§1.3). The one-line fix to the test-only
  `streamReader` is not made either: it changes nothing a user runs (author's
  call).
- **`WriteTo` on the gzip readahead.** No measured consumer copies (mrtcut,
  mrtdump, heldsize and routecheck all read through `Records`). The copy-only
  gzip slowdown it might fix (0.83×, `.data/decompress-v03-gate-gzip.log`)
  stays parked (author's call).
- **Changing `Records`' buffer size.** It would change how much every caller
  reads ahead of a record error.
- **Capping the CLIs' worker count.** v0.3.1's bound stands.

## 4. Anti-goals (a failure even if it works)

- **A different byte or a different error** from `Decompress` or
  `DecompressWith` on any input (v0.3 anti-goal 3, v0.3.1 §4).
- **Slower on real files.** That covers the v0.3.1 speed gate (rv2, rv6 at W4
  and W14) and the v0.3 gzip gate (`Decompress`+Routes vs
  `DecompressWith`+Routes on the rrc00 bview, 1.47×).
- **A fix chosen before the cause is known** (§5.1 measures first).
- **A gate whose pass rule is chosen after its result.** v0.3.1 had to
  change its memory method after a run (its Ruling 9). §5.2 fixes v0.3.2's
  rule now.

## 5. Design

### 5.1 mrtcut on gzip: diagnose, then decide

**Diagnose.** Each run is alone, under the heavy-run rules, and logged
under `.data/`.

- **The series.** `mrtcut -count` on the rrc00 bview `.gz`, in 10 alternating
  pairs: v0.2.1 (`Decompress`) and the branch (`DecompressWith`, Workers =
  GOMAXPROCS). Four runs cannot tell an alternation from noise. Ten pairs
  show whether the two speeds are real and whether v0.2.1 ever shows them
  too.
- **mrtdump on the same file**, in 5 alternating pairs. It uses the same
  `DecompressWith` gzip path but does more work per record, so it shows
  whether the cost is mrtcut's alone. heldsize is not measured: it runs
  Routes, like the v0.3 gzip gate, where the readahead was 1.47× faster.
- **The split.** The same file through decompression alone (`decompbench`'s
  gzip path, `Decompress` vs `DecompressWith`) and through decompression
  plus `Records`. This separates the readahead's cost from record parsing.
- **Profiles.** mrtcut gets a `-cpuprofile` flag; it is a test-only tool, so
  the flag is not API. Take a CPU profile of one slow run and one fast run
  of the branch, plus `GODEBUG=gctrace=1` on one of each. A scheduling cause
  may not show in a CPU profile; then the series and the split are the
  evidence.

**Decide** (author's call; the user opted out of questions). It is decided
per tool, on the mean of its series:

- **Under 3% slower:** noise or a negligible cost. No code change. The
  CHANGELOG gives the figure.
- **3% or more:** try fixes inside the readahead first. Candidates are the
  chunk size, the per-Read `ctx.Err()`, and the goroutine handoff; the
  builder picks, guided by the profile or by the split when the profile
  shows nothing. A readahead fix is kept only if:
  - every slower tool comes within 3% of v0.2.1;
  - the v0.3 gzip gate (`DecompressWith`+Routes) slows by no more than 5%;
  - the 256 KiB queue bound holds.
- **3% or more, and no readahead fix meets that:** each tool that is slower
  opens gzip with `Decompress`. It reads the first two bytes through a
  `bufio.Reader` it adds, and keeps `DecompressWith` for bzip2. This
  duplicates three lines of the library's format check, which is accepted
  for internal tools. No further diagnosis round follows.

Whatever the outcome, the CHANGELOG states the cause as found, or says it
was not found.

### 5.2 Measuring the bound

**The claim.** The bound in the `DecompressWith` doc is on live bytes the
reader holds (v0.3.1 Ruling 9). It is a sum of terms: v0.3.1 §5.3 and its
amendment. v0.3.2 checks it term by term.

**Inputs.** One or more synthetic inputs, built in memory by
`decompbench -crafted` and never committed if larger than `testdata/`
allows (15 MB), that load the terms §1.2 lists:

- **Results finished but not taken:** blocks just under the 2 MiB cap,
  behind a block the chain decodes serially (one over the cap). Workers then
  finish ahead of the chain.
- **Segment copies and the window:** blocks with compressed segments as large
  as the window allows.
- **The exact-size copy:** workers decoding blocks under the cap.

zeros-9 stays as the input for the chain's serial decode and the capped
decodes. The builder decides how many inputs are needed.

**Measurement.**

- Where the reader can count a term, it is counted by test hooks: the peak
  of each term as the reader holds it.
  - `segHeld` already exists.
  - The bytes of results received but not taken, and the window's length,
    need hooks of their own.
  - The hooks are unexported, so the hook-based gate runs as an opt-in test
    in package mrt, enabled by an environment variable as the real-data run
    is (author's call; the builder may choose another route that keeps
    `api/` unchanged).
- Where the reader cannot count a term (a decode's chunks and copy, the
  block table), the GOGC=10 heap peak growth stands for it, as in v0.3.1.

**Pass rule** (author's call, fixed before any run):

- Each counted term's peak is at or under that term's bound.
- The GOGC=10 heap peak growth is under the total bound on every input. If
  it is over while every counted term is under, the gate fails. Then the
  report says so: no new measuring method is chosen after the run.
- The default-GC figure is reported next to it, as in v0.3.1.

**If a term is over its bound:**

- **The code is wrong:** fix the reader. The §6 equivalence and speed gates
  then apply.
- **The arithmetic is wrong:** correct the doc's bound upward. The input
  that exceeded the old term is the measurement the new term stands on.
- **A term no input can reach** (for example, segment copies limited by the
  window before the 32 MiB budget at W4): the doc may tighten that term, and
  says why.
- **The rule either way:** the `DecompressWith` doc and the CHANGELOG change
  whenever the bound changes, with the input that shows it.

### 5.3 (removed)

The first draft fixed `Decompress`'s drained block here. The builder check
found that `Decompress` does not hold one (§1.3), so there is nothing to fix.

### 5.4 Housekeeping

From the v0.3.1 task and final reviews:

- **Zero fixtures to a subdirectory.** `zeros-1.bz2` and `zeros-9.bz2` move to
  `testdata/bzip2/zeros/`, so the three `[^z]*.bz2` globs go back to `*.bz2`
  (fuzz_test.go:293, decompress_with_test.go:89,
  internal/bzip2/bzip2_test.go:21). Fix `testdata/README.md` and every path
  that names them.
- **Test cost.** `TestDecompressWithCappedDamaged` decodes 3 offsets under
  `-race` instead of 5 (about 15 s under `-race`). The redundant re-decode in
  `TestSpeculativeBlockCap` goes.
- **`TestDecompressWithCancelDuringSerialBlock` passes on v0.3.0 too.**
  Rename it to what it pins: a cancel between Reads of capped blocks ends
  with `context.Canceled` and no goroutine left. Its doc says it is a
  regression test; `TestDecompressWithCancelStartsNoJob` pins the v0.3.1 fix.
- **Gaps in Task 1's tests:**
  - **The last zeros-1 block** at a 4 MiB cap is not compared to `Block`'s
    result.
  - **`SpeculativeBlock`'s check before any output** (`maxOut > 0 &&
    bz2.br.err != nil`, block.go:159) is untested. Turning it off passes
    every test, because the check after the output (block.go:137) hides its
    return values. The test needs a side channel, such as the allocation
    delta `TestSpeculativeBlockCap` uses, so that it fails without the
    check.
  - **Nothing tests that extra chunks are dropped** after a capped call.
  - **One test's failure messages skip block numbers.**
- **Docs and tools:**
  - The `internal/bzip2` file comment names `SpeculativeBlock`.
  - `decompbench -blocks` prints no cap when every file failed.
  - `decompbench -mem -crafted` runs with no FILE.

## 6. Tests and gates

- **Equivalence (unchanged rules):** every fixture, the 19 real files
  (`TestRealData/decompress-with/<file>`), `FuzzBzip2` and `FuzzDecompress`.
- **Speed:** the v0.3.1 speed gate (rv2, rv6, W4 and W14). v0.3.2 is within
  5% of v0.3.1, both measured in the same run. If §5.1 changes the
  readahead, the v0.3 gzip gate runs too.
- **Memory:** §5.2, on zeros-9 and on the new inputs, at W4 and W14.
- **mrtcut:** the §5.1 series, before and after any change.
- **Checks:** `check.sh` with `FUZZTIME=15s` ends `check: ok`. `api/` is
  unchanged. routecheck's build errors against the branch equal those
  against v0.2.1.

## 8. Builder check

A builder read the first draft. What they raised, and where it is answered
now:

- **`Decompress` does not use `internal/bzip2`,** so the drained-block fix
  was moot. §5.3 is removed, §1.3 and §5.5 correct v0.3.1, and §3 records
  the change.
- **Live bytes versus heap peak, and a circular rule for changing the doc.**
  §5.2 now has hooks per term, a pass rule fixed before any run, and one rule
  for changing the bound.
- **The window and the exact-size copy were not measured either.** §1.2 and
  §5.2 list them.
- **A slowdown the profile does not explain, and tools besides mrtcut.**
  §5.1 decides per tool, adds an mrtdump series, and runs no further
  diagnosis round.
- **The untested check in `SpeculativeBlock` is at :159, not :137.** §5.4
  is corrected.
- **mrtcut has no `bufio.Reader` of its own.** The fallback adds one.
- **The memguard hashes in `.data/v031-mrtcut-gz.log`** differ because the
  report line includes elapsed time. That is not evidence, and the draft's
  sentence on it is gone.
