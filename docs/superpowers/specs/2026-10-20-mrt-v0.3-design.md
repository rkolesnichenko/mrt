# mrt v0.3: faster decompression

Status: draft · 2026-10-20 · branch `release-0.3.0`

This design amends `2026-10-16-mrt-design.md` (the v0.1 design) where it says
so. CLAUDE.md's principles and rulings hold unless a section below names the
ruling it changes.

## 1. Intent

Reading a RouteViews file is almost all decompression. On the 2026-10-20 RIBs,
`compress/bzip2` takes 84% of a full `Decompress` + `Routes` pass on
route-views6 and 87% on route-views2 (§5). Every user of `mrt` on real data
pays this, and the decoder itself is already fast. v0.3 makes bzip2 files
decompress in parallel and lets gzip decompression overlap decoding, with no
dependency and without changing what `Decompress` does today.

The user asked for this as the next step after v0.2.1 and opted out of a
brainstorming interview. So every choice below that is not measured or settled
by CLAUDE.md is marked as the author's call. The largest of them is §6.2's
copy of the standard library's bzip2 decoder.

## 2. Goals

1. **`DecompressWith(r, DecompressOptions)`**, opt-in. It decompresses a
   bzip2 file with several goroutines, block by block (§6.2), and runs gzip
   decompression ahead of the reader (§6.3).
2. **Output identical byte for byte** to `Decompress`'s, for every input,
   broken inputs included: the same bytes, then an error where `Decompress`
   fails (§6.4).
3. **An explicit lifetime.** Every goroutine `DecompressWith` starts ends when
   the input ends, when decompression fails, or when the caller's `Context` is
   cancelled (§6.1).
4. **`mrtdump` uses it**, so the command speeds up on real files.

## 3. Non-goals

- Changing `Decompress`. It stays exactly as it is: no goroutines, the same
  standard-library readers.
- A pluggable decompressor (the v0.2-era "decompress hook" idea). The parallel
  bzip2 reader is built in, so no caller needs to bring a dependency.
- Parallel gzip. RIS files are one gzip member each (§5), and one deflate
  stream cannot be split without an index.
- Other formats (xz, zstd). Neither RIS nor RouteViews publishes them.
- A bzip2 encoder. Test inputs come from the `bzip2` command (§7).

## 4. Anti-goals (a failure even if it works)

- **A goroutine that outlives its reader.** A caller that stops reading early,
  as `Records` callers often do, must be able to release everything. routecheck
  (the one known consumer) promises context-cancellable code with no
  goroutines it does not own; an opt-in API with a `Context` keeps that true.
- **Any change for an existing caller.** No exported signature changes;
  `Decompress`, `Records` and `Routes` behave as in v0.2.1. The owner's rule:
  nothing in `mrt` may break a consumer without prior agreement.
- **A different byte.** Parallel output that differs from serial output in any
  byte, or that succeeds where serial decompression fails, is a bug, not a
  trade-off. This holds for crafted input too.
- **A dependency.** Root `go.mod` keeps no `require` (principle 3).
- **Unbounded memory or CPU on hostile input** (principle 2). Data in flight
  is fixed by `Workers` and a byte cap, not by anything the input says. The
  wasted work is bounded: each candidate block start is decoded at most once
  speculatively.

## 5. Facts this design rests on (measured 2026-10-20)

Apple M3 Max, Go 1.27.2, `GOMAXPROCS=4`, normal priority, each run alone.

|---|---|---|---|---|---|---|
| rv6-rib.20261020.1400.bz2 | 25,709,978 | 471,448,090 | 6.8 s (69.7 MB/s) | 8.0 s | 84% | `.data/decompress-v03-baseline.log` |
| rv2-rib.20261020.1400.bz2 | 76,399,889 | 1,260,879,356 | 19.7 s (64.0 MB/s) | 22.6 s | 87% | same |
| rrc00-bview.20261020.0800.gz | 425,761,544 | 4,065,645,452 | 5.5 s (736.1 MB/s) | 13.5 s | 41% | same |

A throwaway probe (scratchpad, not in the repository) tested whether blocks
decode independently:
- it found every 48-bit block magic at bit granularity;
- it rewrapped each block as a one-block stream;
- it decoded the blocks with the unmodified `compress/bzip2` on 4 goroutines.

The joined output was identical to the serial output (SHA-256) on both RIBs.
The table is from `.data/bzip2-split-probe.log`:

| File | Blocks | Serial | Scan | Parallel decode | Speed-up (scan + decode) |
|---|---|---|---|---|---|
| rv6-rib | 512 | 7.28 s | 0.17 s | 1.96 s | 3.42× |
| rv2-rib | 1,403 | 20.55 s | 0.52 s | 5.63 s | 3.34× |

The probe held whole files in memory and resolved no false magics. The real
reader uses §6.2's decoder, the same decoding code with exact block ends.
Task 1 measures it again (§7).

- **Rewrapping cannot reproduce the serial reader on broken input.** The
  builder check of this design found three faults in the probe's approach,
  each demonstrated:
  - A block's bits are unbounded, because code lengths are delta-coded in an
    open loop. A `bzip2 -1` stream with 600,000 inserted no-op pairs still
    decodes.
  - "Fails to decode" does not show where a block ends.
  - A one-block wrap never checks the real stream CRC.

  All three come from one cause: `compress/bzip2` does not report where in the
  bitstream a block ended. That is why §6.2 owns the decoder.
- **gzip:** both RIS files checked are a single gzip member,
  rrc00-bview.20261020.0800 and rrc00-updates.20261020.0800
  (`.data/gzip-members-probe.log`).
- **The gzip gain in §6.3 is unmeasured.** Its bound is the time of the slower
  stage: at best rrc00 goes from 13.5 s to about 8.0 s, the decode alone
  (13.5 − 5.5).

## 6. The design

### 6.1 API

```go
// DecompressOptions are the options of DecompressWith.
type DecompressOptions struct {
	// Workers is how many goroutines decompress a bzip2 input in parallel;
	// for gzip, any Workers > 0 runs decompression one goroutine ahead of
	// the reader. 0 is Decompress: no goroutines.
	Workers int
	// Context stops every goroutine DecompressWith started when it is
	// cancelled; Read then returns Context.Err(). Required when Workers > 0.
	Context context.Context
}

func DecompressWith(r io.Reader, opts DecompressOptions) (io.Reader, error)
```

- C1 holds: `Decompress(r)` is `DecompressWith(r, DecompressOptions{})`, and
  both return `(io.Reader, error)`. The apisurface checker enforces that the
  results match, which is why the lifetime is a `Context` in the options and
  not an `io.ReadCloser` (author's call).
- `Workers > 0` with a nil `Context` is an error from `DecompressWith`. Without
  it, a caller that stops reading early would leak goroutines, and the API
  would make that the default (author's call). The error is an unexported
  `errors.New` value, since no caller needs to test for it.
- Uncompressed input is returned as `Decompress` returns it; `Workers` has no
  effect and no goroutine starts.
- No `Workers` default is applied for the caller. A caller wanting "all
  cores" passes `runtime.GOMAXPROCS(0)` (author's call: the library never
  picks a CPU budget for the caller).

### 6.2 Parallel bzip2, on a copy of the standard decoder

A bzip2 stream is a 4-byte header (`BZh` + a level digit), then blocks, each
starting with the 48-bit magic `0x314159265359` and its 32-bit CRC, then a
48-bit end-of-stream magic `0x177245385090` and the stream CRC. Blocks are not
byte-aligned. A file may hold several streams one after another; pbzip2
writes them that way, and `compress/bzip2` reads them all.

- **`internal/bzip2` (author's call).** It is a copy of Go 1.27.2's
  `compress/bzip2` (four files, 869 lines, BSD-3 licence) with the Go LICENSE
  text and a notice. The v0.1 design (§2) already copies rpsl's tools rather
  than importing them, and root `go.mod` still has no `require`. One
  capability is added: decode the block that starts at a given bit offset,
  returning its bytes, its stored CRC, the bit offset where it ended, and the
  error. Everything else (Huffman tables, move-to-front, inverse BWT, RLE1,
  error values) stays the standard code, so the copy fails exactly where the
  original fails.
- **Serial decoding is the ground truth.**
  - A streaming bit reader over the input decodes one block at a time and
    learns each block's exact end.
  - The reader folds the block CRCs into the stream CRC itself and checks it
    at the end magic.
  - After the end magic it repeats `compress/bzip2`'s handling (source lines
    200-230): EOF ends the input; one byte then EOF is
    `io.ErrUnexpectedEOF`; other bytes must start a new `BZh` + level stream,
    or it is an error.
- **Speculation on top.**
  - The caller's `Read` reads the input and scans it bit by bit for block
    magics. Every match is a candidate start.
  - Workers decode candidates ahead, each from its candidate offset to the
    block's own end, working on in-memory copies of the bytes.
  - The ordered reader follows the chain of exact ends. When a block ends at
    offset `e`, it takes the speculative result that started at `e`, if one
    exists. Otherwise (a chain miss) it decodes the block at `e` itself,
    serially.
  - A candidate the chain never lands on is a false magic. It is discarded
    because of its position, never because of a failure, so the false-magic
    question of the first draft disappears.
- **Errors.** Errors come only from the chain, that is, from the same blocks
  in the same order as the serial reader, with the same bytes before each
  error. A failure in a discarded speculation is ignored.
- **No goroutine reads `r` for bzip2.** Only workers are goroutines, and they
  work on in-memory segments. The `Read` that returns EOF or an error first
  waits for every worker to exit, so no goroutine survives a finished read
  (author's call).
- **Bounds (author's call).**
  - Candidates speculated ahead of the chain: at most `2 × Workers`.
  - A speculative segment holds at most 8 MiB of compressed input. A block
    whose end is not within it is decoded serially when the chain reaches
    it, so memory never grows with the block.
  - A decoded block is read into a growing buffer and never preallocated
    from anything the input says. A real block decodes to about 900 KB.
    RLE1 can expand a hostile block about 51-fold, roughly 46.6 MB (the
    builder check's figure, 900,000 / 5 × 259).
  - Worst case in flight: `2 × Workers × (8 MiB + 46.6 MB)`. Typical case:
    about `2 × Workers × 1 MB`.
  - CPU: each candidate is speculated at most once. A crafted file full of
    false magics wastes at most one bounded decode per false magic and
    otherwise runs at serial speed.
- **Allocation.** Each worker can keep its `level × 100,000` `[]uint32` block
  buffer between blocks (3.6 MB at level 9) instead of allocating one per
  decode. This is an option for the builder, not a promise.

### 6.3 gzip readahead

- With `Workers > 0`, one goroutine reads the `compress/gzip` reader, and so
  `r`, into a bounded queue of chunks. `Read` takes from the queue, so
  decompressing the next chunk overlaps the caller's decoding of the last.
- **The queue holds at most 256 KiB of decompressed output** (author's call).
  This keeps `mrtdump`'s promise to stop at once on a failed write:
  `TestMrtdumpWriteErrorStops` fails if more than half of its 287,052-byte
  compressed fixture is read. At its ratio of about 0.2, 256 KiB of output is
  about 50 KB of input. Task 1 measures the gain at this size.
- Concatenated members are still read, as `Decompress` reads them. A broken
  gzip header is still returned by `DecompressWith` itself, as today.
- **After a cancel,** `Read` returns `ctx.Err()` at once. A goroutine blocked
  inside `r.Read` (a pipe, or stdin) exits when that `Read` returns, because
  a `Context` cannot interrupt it. This is documented on `DecompressWith`.
- On EOF or an error the goroutine has already exited (it produced them), so
  a finished read leaves no goroutine.

### 6.4 Equivalence

The property every test of this release checks: for any input and any
`Workers ≥ 1`, reading `DecompressWith` to the end gives the same bytes as
reading `Decompress` to the end. Either both succeed, or both fail after the
same bytes. Error text may differ; whether there is an error may not.

## 7. Tests and gates

- **Task 1 is the gate.** It builds `internal/bzip2` and the reader, and
  measures it:
  - `DecompressWith` at `Workers = 4` on rv2-rib must decompress at least
    2.5× faster than `Decompress` alone, with identical output.
  - With the 256 KiB gzip queue, `DecompressWith` + `Routes` on rrc00-bview
    must be at least 1.3× faster than the 13.5 s baseline.
  - Both thresholds are the author's call. If gzip misses its threshold,
    readahead is dropped from v0.3 and the user is told; a bzip2 miss stops
    the work and goes back to the user.
  - Logs in `.data/`, and every figure in the CHANGELOG comes from them.
- **The copy against the original.** A fuzz target and tests check
  `internal/bzip2`'s serial reader against `compress/bzip2` on arbitrary
  bytes: the same output, and both fail or both succeed. This pins the copy
  before anything is built on it.
- **Equivalence (§6.4)** over every committed fixture, compressed with the
  `bzip2` and `gzip` commands at test time when they are installed, and over
  committed `.bz2` test inputs made by the `bzip2` command, with their
  provenance in `testdata/README.md`:
  - a multi-stream file;
  - a one-byte file;
  - the existing `testdata/bench` file;
  - files cut at many offsets;
  - files with flipped bits;
  - a block padded past 8 MiB with the builder check's no-op code-length
    pairs, which takes the chain-miss path.

  Workers 1, 2 and 8 each.
- **False magics.** A test injects false candidates through an internal test
  hook and checks they are discarded and the output is unchanged. A real
  false magic is too rare to find in a fixture.
- **Cancellation.**
  - Cancelling mid-read makes `Read` return `ctx.Err()`.
  - For bzip2 and for a gzip input that is not blocked, the goroutine count
    returns to its starting value within a bounded wait.
  - A nil `Context` with `Workers > 0` is an error.
- **A fuzz target** `FuzzDecompress`: arbitrary bytes, plus seeds that start
  with `BZh` or `1f 8b`. Property: §6.4 at `Workers = 2`, and no goroutine
  left once a read has returned EOF or an error. It is added to
  `scripts/fuzz.sh` and the CI shards, along with the copy-vs-original
  target.
- **Race detector** over the new tests (`check.sh` runs `-race`).
- **Real data:** §6.4 on rv6-rib, rv2-rib and rrc00-bview, and the
  `mrtdump` goldens unchanged.
- **Consumer check before merge:** routecheck builds and its tests pass
  against this branch in a throwaway copy. The API change is additive, so it
  needs no edit.
- `api/mrt.txt` regenerated; its diff (`DecompressOptions`, `DecompressWith`)
  goes in the CHANGELOG. `check.sh` with `FUZZTIME=15s` ends `check: ok`, and
  an independent reviewer reads the whole diff before merge.

## 8. Left to the builder

- The bit scanner, how segments are copied, and how multi-stream files carry
  each stream's level.
- The exact shape of `internal/bzip2`'s added entry point, as long as the
  standard code paths are unchanged and the copy-vs-original target holds.
- Chunk sizes inside §6.2's and §6.3's bounds; whether gzip readahead and the
  bzip2 reader share their ordering machinery.
- Benchmarks: a `BenchmarkDecompressWith` beside `BenchmarkBzip2` on the
  committed bench file, reported at normal priority.
